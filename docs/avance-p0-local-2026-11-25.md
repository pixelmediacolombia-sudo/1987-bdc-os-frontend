## CAPI-01

- Revisión del recorrido de configuración y entrega en el backend local. La configuración de entorno se indexa por UUID de tenant; el envío persistido usa `meta_dataset_id` y `encrypted_meta_access_token` y el worker descifra el token justo antes de llamar al proveedor.

- Se añadió una prueba regresiva con dataset/token sintéticos. Backend compilado y 10 pruebas focalizadas aprobadas: guard de tenant, configuración por tenant, carga de rutas bajo RLS y errores 400/403 del proveedor simulados sin HTTP, con comprobación de redacción del token.
- En el Docker local, la función `list_qualification_signal_dealers()` devolvió 2 filas, `list_tenant_route_ids()` devolvió 2 y el backend conectado como `bdc_local` vio 2 tenants. Ninguno tiene CAPI habilitado, dataset ni credencial cifrada; uno tiene `qualification_signal_enabled=true`. El worker figura apagado y `META_CAPI_DEALERS_JSON` no está presente. Solo se reportan conteos y presencia.
- Se verificó el aislamiento con dos tenants locales sintéticos y el rol PostgreSQL `bdc`: con el contexto del tenant A, el evento CAPI quedó visible (1); al cambiar al tenant B, no fue visible (0), una actualización cruzada afectó 0 filas y un `INSERT` para el tenant A bajo contexto B fue bloqueado por RLS. Se concedieron permisos temporales dentro de la transacción y el `ROLLBACK` final eliminó permisos y filas; una consulta posterior confirmó cero filas de prueba y que no persistieron esos permisos.
- La revisión encontró que `contacts`, `conversations` y `messages` no tenían RLS. Se reprodujo la brecha de `contacts`: bajo `bdc`, el tenant B veía 1 contacto sintético del tenant A. Se añadieron políticas RLS forzadas por `tenant_id` para las tres tablas y se amplió la prueba para lecturas, actualizaciones e inserciones cruzadas. TypeScript compiló y la prueba focalizada pasó (1/1). Las políticas se aplicaron a la base Docker local; después se confirmó cero filas sintéticas/de prueba, cero grants temporales y RLS habilitado y forzado para las tres tablas.
- Se creó una instantánea local del backend activo y una imagen candidata derivada copiando el `dist` compilado, con `docker buildx --network=none --pull=false`. El candidato se ejecutó en el proyecto `bdc-os-candidate`, con red Docker interna, puerto `127.0.0.1:3001` y volumen PostgreSQL independiente. El backend, PostgreSQL, Redis y Mailpit candidatos quedaron healthy; su migración habilitó RLS forzado en las tres tablas y la prueba focalizada pasó (1/1) usando una cuenta admin sintética. El backend original permaneció healthy y sin reinicio.

- Se completó el análisis de las cinco tablas restantes: `dealer_invitations` ahora tiene RLS forzado por tenant, con lectura de aceptación limitada al hash exacto de invitación y acceso explícito de admin; `user_tenant_memberships` permite el tenant activo, el propio usuario para listar sus dealers y el admin. Migraciones TypeScript compiladas, 19 pruebas unitarias focalizadas aprobadas y prueba RLS Admin en el candidato Docker aislado aprobada (1/1).

## REA-01 y Admin local

- Playwright ejecutó las 12 E2E locales: salud de API/PostgreSQL/Redis, directorio de usuarios, auditoría, configuración, navegación Admin/dealer, logout, contactos y denegación de salud global al rol dealer.

- Los escenarios de usuario/sesión de la suite CRM usan sesiones y respuestas sintéticas interceptadas; los escenarios de salud y directorio usan el backend y PostgreSQL locales. No se usaron contactos reales.
- La suite renovó las capturas locales de auditoría y configuración Admin (`adm-04`/`adm-05`) y las de salud y directorio (`adm-06`/`adm-07`). Se revisaron visualmente; las configuraciones Meta usan datos sintéticos y las credenciales no se muestran.

## Incidente durante compilación local

- Una reconstrucción de Docker iniciada sin aislamiento de red consultó metadatos y autenticación de Docker Hub y llegó a `npm install` en el dashboard, que agregó 23 paquetes. Esas etapas consultaron servicios externos; no se enviaron registros BDC ni credenciales. El build también tenía etapas paralelas para paquetes Debian, clonado de GitHub y descarga de un modelo; el log disponible no permite confirmar hasta dónde avanzaron antes de detener la reconstrucción.
- La reconstrucción completa se detuvo y se intentó de nuevo con `--network=none`; esa ejecución falló por falta de paquetes Debian en caché local y no descargó dependencias. La imagen activa original no se reconstruyó ni reinició; el candidato descrito arriba se construyó por separado sin red. Las siguientes compilaciones completas deberán usar cachés ya disponibles o fallar sin red.
